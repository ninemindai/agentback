# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ESM/Zod/MCP fork of LoopBack 4 — a slim modern subset of `@loopback/core` + REST for building HTTP and MCP services out of the same DI container. ESM-only, Node 22.18+, TypeScript 7.0, pnpm 12 workspaces. Alpha (0.x — all `@agentback/*` packages + the `create-agentback` scaffolder share one lockstep version; `packages/core/package.json` has the current one); API still settling. Scaffold a new app with `npm create agentback my-service [--template rest|mcp|hybrid]`.

For the framework's design thesis (boundary coherence between Zod, OpenAPI, MCP, and DI — and why that matters for AI-led development), see [docs/agent-ergonomics.md](docs/agent-ergonomics.md). Read it before adding a feature that might introduce a second source of truth alongside the Zod schemas.

## Commands

```bash
pnpm install                       # install workspace deps
pnpm build                         # tsc -b across the whole workspace (project references)
pnpm build:watch                   # incremental watch build
pnpm clean                         # tsc -b --clean + rm -rf each package's dist
pnpm test                          # vitest run — IMPORTANT: requires a prior `pnpm build`
pnpm test:watch                    # vitest watch
pnpm typecheck:client              # tsc --noEmit on the esbuild client bundles (NOT covered by build/test)
pnpm verify                        # full local CI mirror: konsistent + check:generated + lint + build + typecheck:client + test + validate-templates + build:site
pnpm build:site                    # render website/dist (fails on a missing/mis-mapped docs diagram, or a broken link)
pnpm konsistent                    # structural-convention check (konsistent.json) — fast, runs on source
pnpm lint                          # eslint + prettier --check
pnpm lint:fix                      # eslint --fix + prettier --write

pnpm -F <pkg> build                # build a single workspace package (e.g. `pnpm -F @agentback/rest build`)
pnpm -F hello-rest start           # run an example (after build)
pnpm -F hello-hybrid start         # REST + MCP from one process
```

Running a single test file or pattern:

```bash
pnpm build
pnpm exec vitest run packages/core/dist/__tests__/unit/application.unit.js
pnpm exec vitest run -t "name of test"
```

## Critical: tests run against built `dist/`, not `src/`

`vitest.config.ts` globs `packages/*/dist/__tests__/**/*.{test,spec,unit,integration,acceptance}.js`. After editing any `.ts` you must `pnpm build` (or have `build:watch` running) before `pnpm test` will pick up the change. The same rule applies to running examples — they `import` from each package's `dist/`.

## Architecture

### Workspace layout

`pnpm-workspace.yaml` includes `packages/*` and `examples/*`. Each package is `@agentback/<name>` and emits to its own `dist/`. The root `tsconfig.json` is a project-references file listing build order; per-package `tsconfig.json` extends `tsconfig.base.json` and declares its own `references`. Adding a new package means: create `packages/<name>/{src,tsconfig.json,package.json}`, add it to the root `tsconfig.json` references in dependency order, and `pnpm install` to wire the workspace symlinks.

### Two layers

1. **Ported faithfully from upstream LoopBack 4** (ESM-ified, `.js` extensions on relative imports, `lodash` → `lodash-es`, `p-event` v6 named exports):
   - `metadata`, `context` — decorator metadata + DI container
   - `core` — `Application`, `Component`, `Server`, lifecycle
   - `http-server`, `express` — HTTP server with graceful stop, Express integration
   - `authentication`, `authentication-jwt`, `authentication-oauth2`, `authorization`, `security` — auth stack (`-oauth2` adds RFC 7662 introspection + JWKS bearer tokens; bring-your-own auth server)
   - `extension-health`, `extension-metrics` — observability extensions
   - `testlab` — test helpers
2. **Rewritten, not ported** (upstream carried too much baggage):
   - `openapi` — Zod-first decorators. Emits OpenAPI 3.1.1 directly from Zod via `z.toJSONSchema({target: 'draft-2020-12'})` instead of the upstream `@loopback/repository-json-schema` pipeline.
   - `rest` — minimal `RestServer` (routing + Zod request/body validation + error mapping + serves `/openapi.json`). Replaces upstream's ~10k LoC of sequences/actions/middleware composition. **Host is a class choice:** `RestApplication` (alias `ExpressRestApplication`) is the Node/Express host; `EdgeRestApplication` is pinned to `listener: 'native'` and installs **no `express`/`cors`** (fetch/Workers/Bun/Deno). The neutral middleware-chain machinery lives in `@agentback/middleware`; `express`/`cors`/`multer` are **optional peer deps** of `rest` (only the Express host / uploads need them). Deploy with `@agentback/cli` (`agentback deploy vercel|cloudflare`).
   - `mcp` — decorator-driven MCP server (`@mcpServer`, `@tool` with `input`/`output` Zod schemas) on top of the official MCP TypeScript SDK **v2** (`@modelcontextprotocol/server`). Runs stdio transport by default. `@tool({ui})` links a `ui://` widget for **MCP Apps** (SEP-1865) — see the MCP Apps note below.
   - `mcp-inspector` — small in-process inspector UI at `/mcp-inspector`; the official `@modelcontextprotocol/inspector` is a CLI, not embeddable.
   - `rest-explorer` — mounts Swagger UI 5.x at `/explorer`.
   - `client` — schema-typed HTTP client. Both ends import the **same Zod schemas**; the client has no `@agentback/openapi` runtime dep (browser-safe). `defineRoute` + `routeGroup` + `safeCall` + typed `responses[status]`. No codegen. See `packages/client/README.md` and the `examples/hello-client` + `examples/hello-rest` pair for the schema-sharing pattern.

3. **New capability packages** (no upstream LB4 ancestor — added on top of the ported core). Each has a README; read it before touching the package:
   - `common` — shared infra utils (hosts `loggers`, the project's logging primitive — see Logging below).
   - `config` — Zod-validated, env-aware config loader (JSONC + YAML) with layered overlays and DI bindings.
   - `drizzle` — the blessed DB recipe: typed Drizzle client binding, lifecycle pool shutdown, `drizzle-zod` re-exports. One artifact chain (Postgres table → Zod → REST route + MCP tool); see `examples/hello-drizzle`.
   - `messaging` + `messaging-bullmq` — transport-agnostic messaging ports (`JobQueue`/`EventBus`/`QueueAdmin`/`Scheduler`) with typed Zod descriptors and an in-memory adapter; the BullMQ package is the durable Redis-backed adapter. See `examples/hello-jobs`.
   - `actors` + `actors-redis` + `actors-do` — a Zod-typed actor runtime: `@actor` service classes with `@actorCommand` methods are compiled (by `ActorRegistry` at `start()`) into a transport-neutral `ActorRuntime` port — stable `{type, id}` address, per-identity serialized turns, idempotent `requestId` replay, rollback on a failed/schema-invalid turn. `InMemoryActorsComponent` is the single-process reference adapter; `actors-redis` is the Redis-backed adapter (per-identity lease coordinates one turn at a time across processes; state + dedup result commit atomically in Lua — the lease token is the sole mutual-exclusion guard); `actors-do` is the Durable Objects adapter (turns run **inside** one object per identity on Cloudflare DO or self-hosted celld — the portable intersection only; state/dedup/journal commit in one atomic multi-key `put`, with each request result in its own `dedup:<requestId>` key so the record never outgrows the platform's per-entry caps — which also caps a turn at 100 events and `requestId` at 256 chars, enforced on every host; the deadline races load+`receive` and the commit runs outside the race, so an abandoned turn never reaches it; journal **read half** only — `registry.events()` works, `registry.subscribe()` throws; **on Cloudflare pass `{baseClass: DurableObject}`** from `cloudflare:workers` — RPC methods are exposed only from classes extending it, and that module exists only inside workerd, so the factory takes it as a parameter; `createInProcessDoActorRuntime()` is the in-process host for tests/dev). Callers (REST controllers, MCP tools) invoke via `ACTOR_REGISTRY` — `invoke(type, id, {name, input}, {requestId})`, or the typed proxy `registry.ref(ActorClass, id).command(input, {requestId})` (pass the class, not the name); actors do **not** auto-project to endpoints, and you must never inject the actor instance and call its methods directly (that bypasses the runtime). State is an explicit method arg/return, never an instance field. Read-only `@actorQuery` methods run **lease-free** (no turn) and join the proxy. A command turn may also return `events` (domain facts); `EventSourcedActorsComponent` is the in-memory adapter that persists them to a per-identity append-only log atomically with state — read via `registry.events(type, id)` / `registry.subscribe(handler)` (state stays authoritative; this is "state + event log", not full event sourcing). `actors-redis` journals the same log durably (per-identity Redis Stream, appended inside the commit script) **and** delivers it by tailing those streams: the log is the source of truth, live delivery is best effort, a reconnecting/restarted consumer replays by `seq` — so **`subscribe` handlers must be idempotent by `(actor, seq)`, and late replay is normal**. **Every turn is deadlined per seat class** — `seatClass: 'capability'` (default, 30s: a caller is waiting) or `'worker'` (10min), with an explicit `deadlineMs` on the definition always winning — because **a timeout is a recorded failed turn, never a wedge**: the caller gets a typed `TurnTimeoutError`, the seat is freed at once, and the failed turn is recorded (journaling runtimes append a reserved `actor.turn.timeout` entry; every runtime logs under `agentback:actors:deadline`, which is the whole record on the journal-free in-memory adapter). That marker is its **own** write touching neither state nor dedup, so the one commit point is untouched and **the timed-out `requestId` stays retryable** — a timeout is not a cached failure result. The turn is **abandoned, not cancelled** (nothing interrupts a running `receive`; its side effects still happened) but it can never commit: each runtime re-checks its mutual-exclusion guard — the Redis lease token, an equivalent per-turn guard in process — immediately before the commit with **no suspension point in between**, and on Redis the deadline races `receive` and only `receive`, never the commit script, so a turn can never both commit and be marked failed (the corollary: on Redis the deadline bounds `receive`, not the commit — a stalled commit makes one caller wait, while the renewal cap still bounds the seat). **The record is gated on turn identity, not error type**: an actor turn may invoke another actor (`@injectActor`), so an inner `TurnTimeoutError` passes through the outer turn's frame — it keeps naming the inner identity/request, only the inner turn is recorded, and to the caller it is an ordinary thrown turn that rolls back (one incident, one marker). On Redis the marker is appended **inside `withLease`, before the release**, so no other process can claim the seat and commit in the gap — the journal records incident order, not issue order. Redis additionally caps lease renewal at the deadline (renewals run every `leaseMs/3`, so the cap is `deadlineMs / renewalInterval`), letting the lease lapse so the seat is claimable across processes even if the holder never returns. See `examples/hello-actors` and [docs/actor-model.md](docs/actor-model.md).
   - `files` + `files-s3` + `files-sdk` — the file-storage `FileStore` port (`put`/`get(key, {range?})`/`stat`/`exists`/`delete` + optional `presignedPut`/`presignedGet`, and a `supportsRange` capability hint) with in-memory and filesystem (`FsFileStore`) adapters; `files-s3` is the S3 adapter (AWS SDK v3 streaming, presigned POST with `maxSize`); `files-sdk` wraps [files-sdk](https://files-sdk.dev) to back the same port with **40+ storage backends** (S3, R2, GCS, Azure, Vercel Blob, fs, …) — peer-dep `files-sdk`, presign/range gated on the backend's advertised capabilities. `get`'s optional `{range}` is the storage half of HTTP range support; `presignedPut` returns a `SignedUpload` (`PUT` URL, or a size-enforced `POST` form when `maxSize` is set). Backs the first-class upload/download recipe (`fileField` + `fileResponse`/`fileDownload`); `serveFile(store, key, {range})` (from `@agentback/rest`) wires the full HTTP `Range` → `206`/`416` path on both hosts. `@agentback/files/testing` ships a shared conformance suite (every adapter runs it). See `examples/hello-uploads`.
   - `model-gateway` — the **model-call seam**, the outbound dual of `extension-rate-limit` and the counterpart of `CoreBindings.FETCH` for the call that costs money. **It is language-model middleware, not a `gateway.call()` API** — an AI SDK `ToolLoopAgent` calls its model directly, so a gateway with its own invocation API would sit _beside_ the agent runtime instead of underneath it and protect only code that remembered to opt in; `wrapModel(model, opts)` returns a drop-in, so `generateText`/`streamText`/`ToolLoopAgent`/`@agentback/agents` all route through it unchanged. `ai` is an **optional peer** imported lazily and the port (`LanguageModelLike`) is declared **structurally**, so no provider-spec version enters the DI surface (the `ChatLike`/`AgentPort` discipline). **The stack order is the design:** `accounting → fallback → retry → breaker → provider`, and two placements are load-bearing — **fallback outside the breaker** (underneath it the secondary's success is recorded as the _primary's_ health and the circuit can never trip) and **breaker inside retry** (each physical attempt votes on health; once open, the remaining retries fail fast). The refusals carry the weight: retry takes 408/409/429/5xx and **never** a 4xx, a cancelled call, or an open circuit (the same request fails the same way forever), always **jitters** (a fleet retrying in lockstep turns a throttle into an outage) and honors `Retry-After` (seconds or HTTP-date; one longer than `maxDelayMs` fails the call at once, since retrying early earns another 429). **The gateway owns retrying**: with `retry` on, its final error is marked `isRetryable: false`, or the AI SDK's own `maxRetries` re-runs the whole stack (9 provider calls and 3 bills per outage at the SDK default); the breaker counts only **provider health**, recording a 4xx as **neutral** — not a failure (one caller's bad input must not take the provider from everyone) and not a success, but it _does_ release the half-open probe slot, or a probe answered with a 400 wedges the circuit shut forever; half-open admits exactly **one** probe, holding a lease that expires after `resetAfterMs` so a stalled probe cannot wedge the circuit. **Fallback secondaries are called raw** (no retry, no breaker); wrap one with `wrapModel(m, {accounting: false})`, never with accounting (the primary bills the call to the model that served it). **Accounting bills in TOKENS, not calls** — closing the gap where `metering` counted one unit per call, which describes traffic and says nothing about spend — and **taps streams** for their `finish` part rather than skipping them (streaming is the common case, so stream-blind metering misses most of the bill). Because a model is built once at boot it cannot know which request it serves, so the principal comes from an **ambient `withModelScope()`** (`AsyncLocalStorage`) that the _unit of work_ opens; **`@agentback/agents` opens one per turn**, so a singleton agent on a singleton model still emits per-principal, per-turn token events sharing the turn's `correlationId`, and `generate({tokenBudget})` caps one turn (checked before each call, so each concurrent call may overshoot by one response — the provider decides how many tokens it emits). Scopes nest (spend counts against every enclosing budget) and are captured when a call starts, so a stream cancelled outside its scope still bills it. **Response caching and tier routing are deliberately out**: an exact-match cache on agent traffic has a near-zero hit rate (every call carries unique history), the semantic cache that would pay needs an embedding dep + threshold policy, provider-side prompt caching is a prompt-_layout_ discipline rather than a gateway feature, and routing needs a which-step-is-cheap policy only the caller can supply. See [docs/concepts/model-gateway.md](docs/concepts/model-gateway.md).
   - `metering` — rail-neutral usage metering for REST + MCP + agent calls (per-principal `UsageEvent`s, pluggable sink, per-principal quota).
   - `agents` — opt-in Vercel AI SDK agent wiring: `toHostTools(app, {include})` projects registered `@tool` classes as an agent's **host-executed tools** through the full `MCPServer.callTool` pipeline (validation, `@authorize` voters, metering hooks; `execute` returns the unwrapped output-validated result, works pre-`start()`; throws at projection time on include typos / duplicates / provider-illegal names / `confirm:` tools — those never project). `installAgent(app, {agent})` binds a **TRANSIENT** turn wrapper (`AgentBindings.AGENT`) that reads the injector context's `SecurityBindings.USER` per turn (identity is per-turn, never baked at projection; transport `REQUEST_AUTH` always wins), preflights quota before the model spends, emits one `'agent'` usage event per turn with tool-call `'mcp'` events sharing `meta.correlationId`, and destroys live sessions on `app.stop()`. `ai` is an **optional peer dep** loaded lazily; the cloud-sandbox `HarnessAgent` path is a manually-verified recipe (experimental `@ai-sdk/harness*` stays out of the lockfile). NOT `actors` (state turns) and NOT `console-chat` (local-tree ACP dock). See `examples/hello-agents` (mock model, zero creds) and [docs/guides/agents.md](docs/guides/agents.md).
   - `command` — the **operator CLI** projection: `buildCli(app, {include})` turns registered `@tool` classes into a hand-runnable command (`my-svc forecast --city Tokyo`), routing every invocation through the same `MCPServer.callTool` pipeline as REST/MCP/agents (validation, `@authorize`, metering, output validation). The sixth projection of the one `@tool` surface; a sibling of `agents` (both consume the shared `selectTools` predicate hoisted into `@agentback/mcp` — `command` uses it directly, `agents.filterTools` wraps it with the AI-provider tool-name check). **`argvToBundle` is the load-bearing seam:** `@tool` inputs are authored `z.number()`/`z.boolean()` for typed JSON, but argv is strings, so it **coerces off the emitted JSON Schema** (via `schemaToOpenApiSchema`) before `callTool` re-validates — booleans as flags (`--verbose`/`--no-verbose`), arrays repeat. **Output is the tool's bare result** on stdout (no `{ok,data}` wrapper — the exit code carries success/failure); errors print an `AgentError` envelope to **stderr** + non-zero exit. `--format text|json|toon` (default by stdout TTY only — **never** sniffs `CI`), `--llms` (manifest of the _selected_ tools), `<cmd> --help` (flags from the schema). Audience is a **human operator/scripter**, not agents (agents already have lossless stdio MCP); `@toon-format/toon` is an optional peer. Tool discovery works pre-`start()` but **invocation needs `app.start()`** (the `bin` owns lifecycle). NOT `@agentback/cli` (that is the `deploy` ops CLI). See `examples/hello-command`, [docs/proposals/cli-projection.md](docs/proposals/cli-projection.md).
   - `payments` — `PaymentRail` seam for REST/MCP calls; ships an x402 (HTTP 402) adapter (MPP/Stripe next). Authorizes payment; does not settle. See `examples/hello-x402`.
   - `cli` — the **lifecycle** ops CLI (bins `agentback`/`abc`): `new` (delegates to `create-agentback`'s exported `scaffold()` — templates are never duplicated, and `npm create agentback` still works; deliberately non-interactive, it points at `npm create` for the wizard), `deploy vercel|cloudflare`, and `update`. **`update` is four phases: resolve → migrate → bump+install → audit, and the first three's order is load-bearing** — bumping first would let a failed install move `from` forward, so the re-run computes an empty `(from, to]` window and silently skips every migration forever. **Every phase is workspace-wide** (pnpm `packages:` globs + npm/yarn `workspaces`): sub-package manifests are bumped, their `src/**` is added to the ts-morph project (tsconfig `references` are not followed — a reference graph is a build-order declaration, and detection needs a file list), and `pnpm-workspace.yaml` `overrides`/`catalog` plus package.json `overrides`/`resolutions` are rewritten, because an override left behind silently re-pins every range the bump just moved (the real blocker in the field, where all three gaps failed _quiet_ and looked like a successful update). The YAML edit is **line-targeted** — quote style, alignment and comments survive byte-for-byte, and a pin it cannot read is reported rather than guessed at; no YAML dep, since npx downloads every dependency on every run. **The audit is the net and the only thing that changes the exit code** (migration notes stay advisory): it re-derives what is on disk from _different parts than the bump_ — a filesystem walk for manifests (not globs), a deep scan for pins (not a section list), a raw-text YAML match (catching the flow style the rewriter refuses), and the installed `node_modules/@agentback/*` versions — because a net woven from the same enumeration cannot catch that enumeration's own bugs. Only a version strictly **below** the target counts. A `Migration` is a **codemod or an advisory** behind one interface (an advisory is a migration with no `apply`), because every breaking change in a tagged release so far is config/behaviour-shaped, not source-mechanical — the two source-mechanical API changes in project history are not ancestors of `main` and no published version ever shipped them. Ships **three 0.9.0 advisories, zero codemods**; the `apply` seam is proven by a fidelity test asserting untouched regions stay byte-identical (scaffolded apps carry no prettier, so a reflowed file is permanent damage), plus a fake migration through `runUpdate` (`MIGRATIONS` is injectable). Because the package is lockstep-versioned it can never contain the migrations for the version it upgrades **to**, so **`npx @agentback/cli@latest update` is the primary invocation** and the CLI refuses when it is older than its target. Detection never boots the app — static source + config reads only. `ts-morph` (vendors its own TypeScript) and `semver` are real deps, not optional peers, precisely because npx does not install optional peers. NOT `@agentback/command` (that projects an app's own `@tool`s as a command surface). See `skills/agentback/references/cli.md` and [docs/proposals/cli-lifecycle.md](docs/proposals/cli-lifecycle.md).
   - `plugin` — discover, gate, mount **and retract** Component-contributing plugins. `loadPlugins` returns a report satisfying `Installed`; `loadPlugin` returns `PluginInfo & Installed`; both build their inverse through one shared `buildTeardown`. **The footprint is the binding snapshot diff `tryMount` already computed** — _not_ the `fromComponent` provenance tag, because `app.component()` instantiates the component **before** tagging (so a constructor that binds directly is untagged) and provenance is last-wins (so it can never name a _displaced_ binding). Four rules the naive version gets wrong, each pinned by a test: (1) **one identity check gates the unbind AND the restore** (`revertOwned` in `@agentback/core`) — an unguarded restore clobbers a third-party shadow exactly as an unguarded unbind deletes one; (2) **a rejected mount rolls back** — `app.component()` runs its side effects before a collision is detectable, and a loser left bound is a leak invisible in `report.mounted`; (3) **shared nested components are refcounted per Application, and their bindings are recorded against the component, not the plugin** — `app.component()` early-returns for an already-mounted nested component, so only the _first_ mount's diff holds its bindings while the mount that must retract them is whichever uninstalls _last_ (`fromComponent` **is** the right attribution for this, and only this); (4) **observers stop through `LifeCycleObserverRegistry.stopObservers`**, gated on `started`/`initialized` — a direct `stop()` bypasses `invokeMethod` injection, group ordering, `disabledGroups` and `parallel`, and third-party `stop()` is not guaranteed idempotent. A partial `strict` load is retractable via the thrown error's report. The marker also takes **`provides`/`inject`** (DI keys): mount order becomes a topological sort with `order:` demoted to a tiebreaker (with zero declarations there are no edges, so `order:` alone governs — unchanged for existing apps), and a duplicate `provides`, unsatisfiable `inject`, or cycle is caught **before any import** — `allowOverride` still permits an intentional duplicate. Declarations are **advisory**: the container stays the authority, so under-declaring costs ordering, not correctness; a key the **app itself** binds satisfies an `inject` with no edge; and the graph cannot express "I need the _overridden_ binding". Several providers of one key under `allowOverride` all get edges, since edging only to the last declarer lets an earlier one mount after the consumer. **An unrecognized marker key warns** (`provide` for `provides`) rather than being dropped — the plugin still mounts, so a swallowed typo is an ordering bug with no visible cause. **A provider outlives its consumers**: retracting a plugin whose `provides` key another _live_ plugin declares in `inject` throws `PluginRetractionBlockedError` naming both, before any teardown work, because a consumer's own cleanup routinely needs the dependency it is losing. LIFO composition already gave that ordering within one report; the guard covers independent handles. It reads the same advisory declarations, so an under-declared `inject` is invisible to it — closing that would mean resolving the container at teardown time. **`mountComponent(app, Class, {name})`** applies that same governance to a class with no specifier — `tryMount` is split at the import boundary, so collision detection, rollback, refcounting and retraction are literally the same code path a disk plugin takes (`source: 'memory'`). **`PluginBindings.REGISTRY`** is live mounted state (`mounted()`, `componentRefs()`) where a report is one run's record; it is bound **before** `appOwnedContext` snapshots in every entry point, because a registry bound inside the first mount window would join that plugin's footprint and be unbound out from under every other mount. **Plugins are trusted code** and this package never governs capability — collisions, ordering and lifecycle only. That scope rests on plugins being first-party or vendored; a real third-party ecosystem is the condition that reopens it, not a reason to assume it already has. **No agent-callable mount tool ships** either: `packages/plugin/README.md` carries it as a recipe, because shipping one ships a default answer to who may rewrite the process. Retracting an `@mcpServer` required fixing `@agentback/mcp` too — see below.
   - `extension-otel` — OpenTelemetry tracing across REST/MCP/jobs (`@opentelemetry/api` only; bring your own SDK/exporter).
   - `extension-rate-limit` — rate-limiting middleware (`rate-limiter-flexible`); in-memory or Redis, with 429 + `RateLimit` headers.
   - `mcp-http` — exposes the in-process MCP server over the MCP **Streamable HTTP** transport, mounted on the REST app's Express. **`protocol: 'both'`** (**the default since 0.9.0**, both hosts) swaps the session machinery for the SDK's `createMcpHandler`, which serves the **2026-07-28** revision _and_ 2025-era traffic from one endpoint — no `Mcp-Session-Id`, one server per request, scales behind a plain round-robin LB. Under it `perSession` becomes per-**request** discovery (its DI context is released when the SDK closes that request's server, after any streamed progress), so wrap expensive binders in **`cachedPerPrincipal`** — the binder now runs on every request. `eventStore`/resumable SSE and GET/DELETE are session features and do not apply. The stdio counterpart is `@agentback/mcp`'s `protocol: 'both'` (`serveStdio`, era pinned per connection), also now the default. **`protocol: 'legacy'` is the one-line rollback on both** — `installMcpHttp` inherits the `MCPServer` config's protocol when its own is unset, so setting it once rolls back stdio _and_ `/mcp` (an explicit value on the mount still wins; `eventStore` without a protocol still yields to sessions), and 2025-era clients keep working under the default either way — verified against three released 1.x SDKs (1.11.0/1.17.0/1.29.0), covering every 2025 revision. One exception keeps the flip safe: setting `eventStore` (resumable SSE, a session feature) **without** naming a protocol keeps the endpoint on `'legacy'`, so a default never deletes a capability the caller asked for by name. **`Origin` validation is on by default on the stateless mount** — every Streamable HTTP revision since `2025-03-26` says servers MUST validate it, so when `allowedOrigins` is unset the policy is _derived_ from `rest.cors` rather than skipped. **Precision follows the source:** a CORS origin string is matched **exactly** (scheme + port), a CORS **RegExp is tested** (so a restrictive dynamic allowlist keeps its protection instead of being discarded), while explicit `allowedOrigins` and the localhost defaults stay **hostname**-matched — the former because that is its shipped documented behaviour, the latter because dev servers move ports. Only a **callback** origin or a true wildcard enumerates nothing; that case **warns** and leaves validation off instead of guessing. Safe to default because a **missing `Origin` passes by design** — only browsers send one. Scoped to the stateless mount on purpose: the session transport exact-matches the raw `Origin` header while the stateless path compares **hostnames** (`toHostnames`, port-agnostic), so a derived `localhost` would 403 a browser on `http://localhost:3000` under sessions. Relatedly, quota measures work performed, via two mechanisms: the limiter **does not debit** a request the SDK's exported inbound classifier says will be rejected (bad JSON-RPC shape, a batch carrying modern elements, or an `Mcp-Method`/`MCP-Protocol-Version` header disagreeing with the body → `-32020`), and it **refunds** (`reward()`) when the transport answers 4xx for a rung the classifier cannot see (a _missing_ standard header is validated in an un-exported SDK function). A tool that runs and throws answers 200 and stays debited, and `tallyToolCalls` counts every batch element, so one rejected POST could otherwise drain a bucket — which bites hardest on the fetch host, where every anonymous caller shares one `anon` bucket. It decides _whether to debit_ only and never answers; the SDK still renders the rejection, so the wire format has one owner. See [docs/proposals/mcp-2026-stateless.md](docs/proposals/mcp-2026-stateless.md). ### Schema-on-decorator routing (REST + MCP share this shape)

**REST verb decorators and `@tool` both put Zod schemas on the decorator and derive the handler's input type via `z.infer`.** No per-parameter `@param`/`@requestBody`/`@response`/`@arg` decorators — those were removed. The pattern:

```ts
const HelloPath = z.object({name: z.string().min(1).max(64)});

@get('/hello/{name}', {path: HelloPath, response: Greeting})
async hello(input: {path: z.infer<typeof HelloPath>}) { … }

@tool('forecast', {input: ForecastIn, output: ForecastOut})
async forecast(input: z.infer<typeof ForecastIn>) { … }
```

Rules to keep in mind when editing route/tool code:

- **Slot 0 = validated input bundle when any schema is declared.** For REST: `{body, path, query, headers}` (only the keys you declared). For MCP: `z.infer<typeof input>`. The decorator's `TypedPropertyDescriptor` enforces this at compile time — a wrong parameter type errors at the `@verb` / `@tool` line with the property mismatch surfaced precisely.
- **Slot 0 is unconstrained when no schemas are declared.** `@get('/whoami') async whoami(@inject(USER) user) {}` is valid; `@tool('ping') async ping() {}` is valid.
- **`@inject` lives at slot 1+** when schemas are declared. Putting `@inject` at slot 0 alongside a schema throws at decoration time with the class+method+verb in the message.
- **`response:` / `output:` constrain the return type.** When set, the method's return must satisfy `z.infer<typeof response>` (or `Promise<…>`) and is validated at runtime — logged on mismatch for REST, thrown for MCP.
- **`status:` on REST route options** overrides the default 200. Status 204 returns an empty body.
- **URL placeholders must match the `path:` schema's keys.** Checked at `app.start()`; mismatches throw with the controller+method named.
- **REST header schemas use lowercase keys.** Incoming headers are normalized before validation so `headers: z.object({'x-trace': z.string()})` finds the value regardless of how the client sent it.
- **MCP `@tool` `input:` must lower to an object root.** MCP `inputSchema` needs named properties at the root, so the schema must be a `z.object(...)` (a top-level `z.union`/`z.discriminatedUnion`/primitive, or a `z.intersection` Zod cannot merge into one object, is rejected at registration with the tool named — the check runs on the **emitted** schema, so since Zod 4.6 an intersection of two plain objects is accepted). Express cross-field invariants with `.refine()` on the object — but note `.refine()` is validated at runtime only and is **not** reflected in the emitted `inputSchema` (`z.toJSONSchema` silently drops it), so document the rule in the field descriptions too.

Where the registrations live:

- Verb decorators store `RouteOptions` on `RestEndpoint` metadata + a per-route Zod bundle in `zod-bridge.ts`'s `routeRegistry`. `RestServer.makeHandler` reads the registry and weaves with `resolveInjectedArguments`.
- `@tool` stores `input`/`output` on `ToolMetadata`. `MCPServer.dispatchTool` parses input, resolves the tool **instance through its own binding** (`MCPServer.resolveMember`, so constructor `@inject` is honored), calls `resolveInjectedArguments` to weave method-level injects, applies the method, then validates output.

### `@mcpServer` and `@api` class tagging

`@mcpServer()` is `@injectable({scope: SINGLETON}, extensionFor(MCP_SERVERS))` under the hood — a tool class is a DI **service** that is an _extension_ of the `MCP_SERVERS` extension point, singleton by default (pass `@mcpServer({scope, tags})` or `@mcpServer('name')` to customize). **Register tool classes with `app.service(...)`** — a tool is a service. The MCP server discovers them via `ctx.find(extensionFilter(MCP_SERVERS))` and resolves each instance through its own binding (`resolveMember`), so constructor `@inject` works regardless of namespace (`service`, `controller`, or a manual `bind().apply(extensionFor(MCP_SERVERS))`). When you `app.service(SomeClass)`, `createServiceBinding` reads the class's bind metadata and tags the binding automatically — never call `.tag()` manually.

`@api()` REST controllers are discovered by the core `controller` tag (`CoreTags.CONTROLLER`) — `RestServer` does `ctx.findByTag(CoreTags.CONTROLLER)` and mounts the `@api`/`@verb` routes of each (a class with no route metadata is a no-op). `app.restController(C)` is a thin alias for `app.controller(C)` that exists for call-site readability; it adds no separate tag. A **dual REST + MCP class** (`@api` + `@mcpServer`) needs only **one** registration: `app.restController(C)` (or `app.controller(C)`) tags it `controller` (→ REST) and — because `restController` is _additive_ and honors the class's `@mcpServer` metadata — keeps its `extensionFor(MCP_SERVERS)` membership (→ MCP). Do **not** also call `app.service(C)` for the same class: explicit `controller` + `service` calls deliberately produce **two** bindings, and with no collect-time dedup the MCP server would register the tool/resource twice. (Component registration is the exception — listing a class in both `controllers` and `services` arrays yields a single merged binding.)

### What's available vs deferred vs out of scope

**Out of scope** (the rewrite walked away from these deliberately — don't add them back):

- LB4 sequences/actions (`findRoute → parseParams → invoke → send → reject`). `RestServer.dispatch` is a single fixed pipeline; per-route customization lives on decorators, cross-cutting in middleware/interceptors, deeper changes via subclassing `RestServer` and overriding `dispatch` / `sendResult` / `sendError`.
- `@loopback/repository` and `Filter<T>` / `Where<T>` helpers.
- `x-ts-type` inlining (Zod schemas replace it).
- `@oas.deprecated` / `@oas.tags` / `@oas.visibility` decorator namespace.

**Available**, callers just need to know it exists:

- **Middleware chain** — `app.middleware(fn)` and `app.expressMiddleware(factory)` from `MiddlewareMixin(Application)`. The chain is mounted as the **first** Express handler in the `RestServer` **constructor** (matching upstream LB4's `ExpressServer`), so it fronts _every_ route — including ones `install*` helpers (`installMcpHttp`'s `/mcp`, `installExplorer`, `installConsole`, …) mount before `app.start()`. `toExpressMiddleware` resolves and **group-sorts** the chain lazily per request, so middleware bound any time before the first request still participate. Order is governed by group tags + `upstreamGroups`/`downstreamGroups` topological sort (`MiddlewareView`), not registration order. The `MiddlewareContext`'s `request`/`response` are the standard Express objects. _(Don't mount middleware behind `start()`-mounted routes by adding `app.use` after construction — use `app.middleware` so it joins the chain.)_
- **CORS + body parsing are chain entries, not bare `app.use`** — `RestServer.registerBuiltinMiddleware` registers `cors` (group `RestMiddlewareGroups.CORS`) and the body parsers (group `parseBody`) **into** the chain, so the topological sort runs them `cors` → `parseBody` → your `middleware` group. **CORS**: `RestServerConfig.cors` — `true` for defaults, or `CorsOptions`. **Body parsing**: `RestServerConfig.bodyParser` — omit for JSON-only (the default), `false` to mount none (consume the raw stream / accept arbitrary media types yourself), or `{json?, urlencoded?, text?, raw?}` (each `true` or the matching Express parser's options) to accept media types beyond `application/json`. Position your own middleware relative to these with `app.middleware(fn, {upstreamGroups/downstreamGroups: [RestMiddlewareGroups.PARSE_BODY]})` — but a middleware in the default `middleware` group can't also point downstream at `parseBody` (parseBody already runs ahead of `middleware`; that's a cycle) — give it its own group.
- **`PORT`/`HOST` env** — `RestApplication`'s constructor resolves the server's port/host from three sources, highest precedence first: explicit `new RestApplication({rest: {port}})` config → `process.env.PORT`/`HOST` (12-factor deploys) → the defaults (`3000`/`127.0.0.1`). Env only fills a field the caller left unset, so explicit config is never clobbered; a malformed `PORT` warns and falls back, `PORT=0` is honored (ephemeral).
- **Subclassable dispatch** — `RestServer.makeHandler` / `dispatch` / `sendResult` / `sendError` are all `protected`. Subclass for envelope wrappers, custom error shapes, request-scoped tracing, etc.; bind the subclass via `app.server(MyRestServer)`.
- **HTTP upgrade (WebSocket) on the app's port** — `RestServer.upgrade(path, handler, {close?})`. Node emits an `Upgrade` request as a separate `'upgrade'` server event, never through the request handler, so this is the only supported way to put a `ws` endpoint beside the REST routes (never read the private `httpServer`). Register **before `start()`** (after, it throws); one listener is installed when `start()` creates the server, on both the Express and native listeners, and **only if a path is registered** — with none, Node keeps downgrading upgrades to plain requests, so existing apps are unchanged. Exact pathname match; unmatched → `404`, malformed request-target → `400` (parsed inside a try/catch: a throw escaping an `'upgrade'` listener is an uncaught exception that kills the process before any auth runs); a throwing/rejecting handler just loses its socket. Handlers are not middleware — auth is theirs. **`stop()` awaits each `close` hook, then destroys every accepted socket still open**, because an upgraded socket is no longer an HTTP connection and `server.close()` would otherwise wait on it forever (measured, and pinned by a mutation-checked test). Node listener only — nothing under `listen: false` or on a fetch host.
- **Unbinding an `@mcpServer` retracts its tool** (`findToolBindingKey`, the MCP counterpart of REST's `findControllerBindingKey`). `registerAllOn` bakes a `visible` map when a server is built, so both SDK handlers consult liveness per request — a retracted tool disappears from `tools/list` and takes the same not-found path as an unknown name on `tools/call`. `resolveMember`'s `new ctor()` fallback is **gone**: a missing binding throws, because silently running user code with un-injected dependencies is strictly worse than a typed error (the removal also covers resources and prompts, which are discovered the same way). Before this, an unmounted tool stayed callable _and_ ran without DI. **Connected clients are told:** `MCPServer.onListsChanged(fn)` watches the `MCP_SERVERS` extension point (one `ContextView`, bursts coalesced into one call) and every connection that can carry it gets `notifications/{tools,prompts,resources}/list_changed` — 2025 sessions and stdio directly (`sendListsChanged`), 2026-07-28 HTTP clients through `createMcpHandler`'s `handler.notify` → `subscriptions/listen`. **`buildServer({listChanged})` defaults to `false`**, because the SDK advertised `listChanged: true` on every server with nothing ever sent; a host passes `true` only for a connection it forwards to. Two connections cannot carry it and say so: a 2025 client on the stateless mount (one server per request, no standing stream) and a 2026-07-28 client over stdio (`serveStdio` exposes no event bus — an SDK gap). On a 2025 session the notification rides the standalone GET stream, so one announced before the client opens it is lost unless an `eventStore` is set.
- **Every `install*` helper returns an `Installed`** (`{uninstall(): Promise<void>}`, from `@agentback/core`) — the revertible-install contract: `uninstall()` retracts the helper's full footprint (routes 404 again on both hosts via gate flags — Express cannot unmount a layer — plus fetch-handler removers, binding unbinds, lifecycle-hook deregistration, transport/session close), idempotent, LIFO-composed via `composeTeardown()` (`@agentback/common`). Callers that ignore the return value are unaffected. Two load-bearing side effects of the same work: **unbinding a controller retracts its routes as 404** on both hosts (per-request `findControllerBindingKey` gate — previously a resolver 500), and **`addFetchHandler`/`addFetchPrefix` return removers** (the native listener re-reads the memoized `fetchHandler()` per request so removals propagate). A new `install*` helper must follow the contract and add a `runInstallConformance(...)` test (`@agentback/testing`); write an async one's body with **`installSteps`** (`@agentback/common`) — an async generator that `yield`s each step's inverse as the step lands (before anything that can throw on it), so a failure part-way rolls back exactly what landed, with no hand-written `catch → teardown.run()` at each exit. Known carve-outs + design rationale: [docs/proposals/revertible-installs.md](docs/proposals/revertible-installs.md).
- **`AgentError` for client-correctable domain errors** — `@agentback/openapi` exports `AgentError`, a transport-neutral error carrying `status`/`code`/`message` (plus optional `issues`/`hint`/`schema`/`retryable`) that `buildErrorEnvelope` reads. A plain `Error` thrown from a service or `@tool` is redacted to a generic 500 (`internal_error`, "Internal Server Error") on both surfaces — its message never reaches the caller; `throw new AgentError('Provide a city or coordinates.', {code: ErrorCodes.INVALID_INPUT})` (defaults to 400) preserves it. REST-specific `invalidParameter`/`invalidRequestBody` still exist; use `AgentError` in cross-transport domain code.
- **Cancellation is one seam: `CoreBindings.ABORT_SIGNAL`** — every entry point that owns a cancellable unit of work binds an `AbortSignal` into that unit's context, and DI's chain walk carries it to anything nested (a service, a projected `@tool`, an agent turn). Bound by: `RestServer.invokeRoute` and the Web `RestHandler` (client disconnect — a Node `close` event is only a disconnect when `!res.writableEnded`, otherwise every completed request would abort its own signal), `MCPServer.requestContextFor` (the SDK's `extra.mcpReq.signal`, i.e. `notifications/cancelled`), `callTool`'s `{signal}` option (shadowing the parent context — an explicit per-call signal is a narrower statement than the turn's), and `AgentTurnOptions.abortSignal`. **A queue job is the exception:** `@jobProcessor` methods get no per-job DI context, so its signal is the `JobContext.signal` field, not a binding — hand `job.signal` on explicitly. **Always `@inject(..., {optional: true})`** — a plain service call has no ambient unit of work and `undefined` is the honest answer. The reason is always a `DOMException` named `AbortError` carrying an `AbortReasons` message (`@agentback/common`, with `abortError()`/`isAbortError()`), because hosts disagree on their own abort reasons — the fetch path re-expresses the host's signal as ours so a route reads the same on workerd/Bun/Deno/`@hono/node-server`. **The agent turn reads the ambient signal and forwards it to the model**, so a caller who hangs up stops the generation rather than paying for tokens nobody reads. A `streamOf` route's signal also fires on `app.stop()` (`CANCELLED`): a stream has no natural end, so a graceful stop ends it rather than waiting forever, and a slow reader pauses the producer (backpressure on every host). **One route option inverts this deliberately:** a `@get(..., {streamOf, resumable})` route keeps its producer alive across a dropped connection, so its signal follows the **stream** (resume-window expiry or server stop — never normal completion) and not the socket — wiring the socket's signal there would abort the generation the instant the client blinked and defeat the feature. See [docs/concepts/cancellation.md](docs/concepts/cancellation.md).
- **`WorkerOptions.timeoutMs` is the wall-clock backstop for a job attempt** — opt-in, no default (an unbounded handler is unchanged). An agent job has no natural end and a retry cap counts _attempts_, so a run stalled **inside** an attempt stops counting while it keeps billing; only a clock ends that. Three load-bearing properties, all pinned by the shared messaging conformance suite so both adapters answer identically: the attempt is **abandoned, not killed** (Node cannot interrupt running code — the signal aborts, the attempt is recorded failed, the seat is freed, and a handler that ignores its signal runs on unread; the same bargain `actors` strikes for a turn deadline); it is **never retried** even under `attempts: 3` (redelivering a hang buys the same hang on the next worker — on BullMQ enforced with `UnrecoverableError`, because with late acks a plain throw _is_ redelivered); and **`cancel()` on a started job aborts that attempt's signal**, which reaches only a worker **in this process** — a job running elsewhere answers `false` and means it. Cross-process cancel needs a side channel and is deliberately not implied.
- **Injectable `fetch` seam** — `CoreBindings.FETCH` (typed `Fetch = typeof globalThis.fetch`, exported from `@agentback/common`) is the DIP boundary for outbound HTTP. A domain service that calls an external API should inject it instead of reaching for the global, so tests bind a stub with no network: `constructor(@inject(CoreBindings.FETCH, {optional: true}) private fetch: Fetch = globalThis.fetch) {}`. Override in tests via `createTestApp(App, {overrides: {[CoreBindings.FETCH.key]: stub}})`.
- **`createTestApp` is the testing default** — `@agentback/testing`'s `createTestApp(AppOrFactory, {overrides, config, mcpScopes})` boots the app on an ephemeral port and returns `{app, url, client (typed), http (supertest), mcp (in-memory MCP client), call(), stop()}` and is `await using`-disposable. Prefer it over hand-rolling `getServer('MCPServer')` / `buildHttpApp({port:0})` in app tests — see `packages/testing/README.md`.
- **`new RestApplication({rest: {...}})` configures the RestServer** — the constructor's `rest` key is forwarded to the `servers.RestServer` config binding, so `{rest: {port, host, basePath, cors}}` works directly. A later `app.configure(RestBindings.SERVER).to(...)` still overrides it (last write wins).

### Logging

**`loggers` from `@agentback/common` is the single logging primitive — use it everywhere.** Do not import the `debug` npm package directly in any package (the one exception is `common/src/utils/debug{,-factory,-pino}.ts`, which _implement_ `loggers` on top of `debug` and pino).

`loggers(namespace)` returns a `{error, warn, info, debug, trace}` record — each entry is a `Debugger` (callable, has `.enabled`), backed by a sub-namespace (`ns:error`, `ns:debug`, …). On top of raw `debug` it adds: level routing, secret redaction (`redactData`/`maskSecret`), an `onLog(hook)` sink for shipping warn/error events to external systems, optional pino structured-JSON output, and `DEBUG_DEPTH` inspect control. The usage shape:

```ts
import {loggers} from '@agentback/common';
const log = loggers('loopback:context:binding');
if (log.debug.enabled) log.debug('Get value for binding %s', this.key);
```

**Namespace note:** because each level is a sub-namespace, a `loggers('foo:bar')` line logs under `foo:bar:debug` (etc.), not `foo:bar`. Set `DEBUG=foo:bar:*` (or `foo:bar:debug`) to see it. The ported LB4 packages were migrated off raw `debug` to `loggers` in one pass; everything maps to `log.debug` (raw `debug` ≈ debug level) unless a call is semantically a warn/error.

**File uploads / downloads are first-class** (no longer an escape hatch). A `fileField()` (from `@agentback/openapi`) on a route's `body:` schema flips the request to `multipart/form-data` (emitted in OpenAPI as `format: binary`), auto-mounts a per-route multer parser that **streams** each file to the bound `FileStore` (`@agentback/files`) under a **server-generated UUID** key, and delivers `UploadedFile` handles in the validated slot-0 bundle. Downloads `return fileResponse(...)` / `fileDownload(retrieved)`, which `RestServer.sendResult` pipes (Content-Type/Disposition) instead of JSON-encoding; `serveFile(store, key, {range})` adds full HTTP `Range` → `206`/`416` support (video seek, resumable downloads) on both the Express and edge hosts, advertising `Accept-Ranges` only when the store's `supportsRange` allows. `FileStore.stat(key)` returns metadata without transferring the body (the cheap HEAD path), and `get(key, {range})` reads a byte slice. Storage is a port: `InMemoryFileStore` (dev/tests, on the `@agentback/files` barrel) or the disk `FsFileStore` (Node-only `@agentback/files/fs` subpath) or `S3FileStore` (`@agentback/files-s3`) or any of [files-sdk](https://files-sdk.dev)'s 40+ backends via `FilesSdkFileStore` (`@agentback/files-sdk`). `RestBindings.HTTP_REQUEST`/`.HTTP_RESPONSE` are bound per request for raw-stream escape hatches. See `examples/hello-uploads`. (`multer` is now an **optional peer dependency** of `rest`, loaded lazily by the Express upload path; the fetch/edge path parses multipart with Web `FormData`, no multer.)

**Resumable SSE is opt-in per route.** `@get(..., {streamOf, resumable: {windowMs?, maxEvents?}})` puts an `id:` on every SSE frame and keeps the producer running for `windowMs` (default 30s) after a disconnect, buffering `maxEvents` (default 1024). A reconnecting `EventSource` resumes through the standard `Last-Event-ID` header with **no client code**, and — the point of the whole feature — **the handler is not re-invoked**, so a browser refresh no longer throws away an in-flight agent turn. Both hosts implement it (the Express `sendStream` and the Web `toStreamResponse` share one `ResumableStreamRegistry` per server; `resumable-sse.integration.ts` runs on express, web-dispatch and native hosts). The refusals carry the design: **a `Last-Event-ID` that cannot be honoured is an HTTP 409** (`conflict` envelope) — unknown, expired, trimmed out of the ring, or opened on **another route or by another principal** (a stream is bound to `(route, owner)`), all indistinguishable — so `EventSource` stops instead of looping, and **the handler is never re-run** for a well-formed id (a fresh run would be the duplicate turn the feature exists to prevent). On an anonymous route the stream id is therefore a **bearer capability**, and it is never logged. **Live streams are capped server-wide** (`rest.resumable.maxLiveStreams`, default 1000): past it a _new_ stream gets 503 + `Retry-After` before the handler runs (a slot is reserved at the gate, so concurrent slow-first-item requests cannot overshoot); a resume is never capped. The handler's signal aborts on window expiry (`RESUME_WINDOW_CLOSED`) or `stop()` (`CANCELLED`, which also ends connected clients), **never on normal completion**. `resumable` + `format: 'jsonl'`, `resumable` without `streamOf`, and a non-integer/`< 1` `maxEvents` or non-finite/`<= 0` `windowMs` all throw at decoration time. The buffer is in memory, so resumption is **single-process** — the same trade `InMemoryEventStore` makes in `@agentback/mcp-http`. Distinct from `idempotency:` (still mutually exclusive with `streamOf`): that replays a _finished call's cached result_, this replays a _live stream's missed frames_. See [docs/guides/streaming.md](docs/guides/streaming.md).

MCP HTTP transport **is** implemented — `@agentback/mcp` runs stdio by default, and `@agentback/mcp-http` adds the Streamable HTTP transport mounted on the REST app's Express (per-session isolation). See the New capability packages list above.

**Two invariants the stateless default depends on** (both were violated in 0.9.0 and fixed after review — the shared cause is that stateless builds a fresh `MCPServer` per **request**, so anything the session path got for free by living once per session must be re-derived):

1. **Scope filtering must pass `[]`, never `undefined`, when auth is configured but the caller is anonymous.** `buildServer()` skips scope filtering _entirely_ when `scopes` is `undefined`. The stateless factory wrote `authInfo ? {scopes} : {}` — which looks equivalent to the session path's `authEnabled ? (scopes ?? []) : undefined` and is not. Under `strategyAuth: {required: false}` an anonymous caller got `undefined` and every `@tool({scope})` became **visible and callable** — `@tool({scope})` is a visibility gate, so nothing downstream re-checks it. `perRequestFactory` now takes `authEnabled` explicitly.
2. **`MCPBindings.CONFIRMATION_STORE` is bound app-level by `MCPComponent`.** A `confirm:` round-trip spans two requests; an instance-level fallback store vanished between them under `perSession` + stateless, so every valid token was rejected as `confirmation_invalid` and the tool could never run. Bind your own (Redis) for multi-instance. `MCPBindings.SUBSCRIPTION_STORE` (MCP Events) is app-level for the same reason: `events/subscribe` and the emit that delivers to it are different requests, and the stateless server that answered the subscribe is gone before the first delivery.

**`confirm:` picks its presentation per request (S6).** A `confirm:` tool is one mechanism with two faces: on the **2026-07-28** era, when the client **declared the `elicitation` capability**, `enforceConfirmation` returns a native `input_required` result so a conformant host renders a real confirmation dialog (one `callTool` from the caller's side — the SDK completes the round trip). Everyone else — the 2025 era, a modern client that cannot prompt, and every programmatic path (`callTool`, `@agentback/command`, `@agentback/agents`) — gets the original `confirmation_required` token dance. **Era alone is not the gate**: the SDK raises `MissingRequiredClientCapability` for an elicitation the client never declared, so gating on era would turn a confirmation into a hard protocol error. The era discriminator is `ctx.mcpReq.envelope` (absent on 2025); capabilities come from its `CLIENT_CAPABILITIES_META_KEY` entry. **The `ConfirmationStore` stays the sole authority on both paths** — MRTR `requestState` only _transports_ a token the server already issued (single-use, TTL'd, fingerprinted to the exact input), because `requestState` is client-echoed and the spec treats it as attacker-controlled with no replay defense of its own. On the elicitation path an **affirmative** answer is required — the response must be `kind: 'elicit'`, `action: 'accept'`, carrying `confirm: true`. A missing, malformed, declined or cancelled response does not run the tool even with a valid token: `requestState` proves a round trip happened, not that a human said yes. See `confirm-mrtr.unit.ts` for the forge/replay/tamper tests.

**Elicitation — `@inject(MCPBindings.ELICIT) elicit: Elicitor` (P1-7 phase 2, experimental).** `elicit.ask(key, {message, standard: FlatZodObject, extended?})` / `askAll({...})` asks the user mid-call. `elicit.once(key, fn)` runs expensive pre-ask work **once per call, not once per round**: the first round seals its JSON result into the request-state envelope (`once`) next to the answers and later rounds replay it — **every round, the first included, gets the JSON form** (a `Date` is a string); signed, not encrypted, so never a secret; 32 KiB cap; a throw is not stored; **not single-use** (a caller can replay a round's envelope on a new call with the same input within the hour, so never freshness- or authorization-sensitive data); with nobody to ask it just runs `fn`. The **MCP Inspector answers questions**: a tool that injects `ELICIT` runs through an in-memory 2026 client in manual MRTR mode (`inputRequired: {autoFulfill: false}`), each `input_required` round comes back to the page as `{inputRequired: {questions, requestState}}`, and `POST /tools/{name}/answer` continues the call. `confirm:` tools take the same path (asked natively), `?as=` is refused for them, a `protocol: 'legacy'` server gets a clear `elicitation_unavailable`, and a tool error keeps its code with the status recovered from it (the MCP envelope carries no `statusCode`). **The tool body re-runs from the top every round, on every era** (ask before side effects): an unanswered `ask` throws an `InputRequiredSignal` the dispatcher turns into `input_required`, and the next round replays earlier answers. Who can be asked follows `MCPBindings.REQUEST_CLIENT` (`{era, capabilities?, info?, canRoundTrip}`, bound per SDK request): a 2026 client that declared `elicitation` answers via MRTR; a **2025 session or stdio** client that declared it is asked by the SDK's **legacy shim** (it sends a real `elicitation/create` and re-invokes the handler); a **stateless 2025 request** (never saw `initialize`, holds no connection), a client without the capability, and in-process `callTool` get `AgentError` `elicitation_unavailable` — decided by the framework **before** the SDK would raise `MissingRequiredClientCapability` or a non-envelope `isError`. **One signed envelope carries both `confirm:` and answers**: `{v, tool, fp, sub?, confirm?, confirmed?, answers?, once?}` (`fp` is the input's fingerprint and the whole envelope is client-readable) minted with the SDK's `createRequestStateCodec` **used standalone** (the SDK's server-wide `requestState.verify` hook would change what `requestState()` returns for every handler and reject `confirm:`'s tokens), keyed by `MCPBindings.REQUEST_STATE_KEY` (`AGENTBACK_MCP_STATE_KEY`, else random per process — **multi-instance must share one key**; a verification failure is logged, a short key fails `start()`), valid for an hour. It is bound to the tool name, an input fingerprint and the caller (`sub`), so state cannot be swapped between calls or callers; a bad/expired/foreign envelope is refused (`confirmation_invalid` for `confirm:` tools, `invalid_input` otherwise). The signature proves the server minted it, **not that it was used once**, so the `ConfirmationStore` stays the single-use authority, with **three store scopes**: the token-dance token (`tool:<name>`, accepted only as the `confirmationToken` input), the prompt token (`#prompt`, accepted only from the envelope and **always** together with an affirmative answer — never skipped because a retry dropped `elicitation`), and a **fresh** `#confirmed` token carried across a `confirm:` tool's own question rounds (envelope TTL, not the prompt TTL). **Request state is read only from `REQUEST_EXTRA` bound on the request's own context** (`ownExtra`): a tool called in-process from inside another MCP request (an agent turn, nested `callTool`) must not inherit that request's state or answers. Answers sealed in the envelope were validated when accepted; `inputResponses` are validated against `standard` every time. Guards throw `ElicitMisuseError` (ask after a stream tool's first `yield`, the reserved key `confirm`, a repeated key, a non-flat form) or a "swallowed the signal" error (a tool that catches the signal and returns or throws something else). Cross-cutting: `McpDispatchInfo.inputRequired` is set after `next()`; metering bills only the final round (`Meter.observe(..., {skip})`); the price gate authorizes every round (idempotent); the rate limiter debits every round (each is real traffic). `selectTools` (agents/CLI projections) excludes any tool whose method injects `MCPBindings.ELICIT`. `MCPServer.serveTransport(transport)` serves both eras over any transport; `createTestApp({mcpEra: 'modern', mcpElicit})` drives the re-run in tests. Q1: TS SDK clients strip vendor keys on individual form properties (`x-openai-*` inside `properties`) but keep top-level extras — design `extended` forms to degrade.

**MCP Apps (SEP-1865) — `@tool({ui})`.** A tool can ship an interactive `ui://` widget a conformant host (Claude Desktop / Goose / VS Code) renders inline for its result. `@tool(..., {ui: {resourceUri, visibility?}})` emits `_meta.ui` on the `tools/list` entry; a `@resource('ui://…', {mimeType: MCP_APP_MIME_TYPE})` (`MCP_APP_MIME_TYPE` = `text/html;profile=mcp-app`, exported from `@agentback/mcp` alongside `ToolUiMeta`/`ToolUiVisibility`) returns the widget HTML; the host feeds the tool result's `structuredContent` (so declare an `output:` schema) to the widget. The resource side reuses existing primitives — `dispatchResource` passes the MIME through and `resources` is already an advertised capability — so the only framework seam was the tool `_meta.ui`. **The widget MUST connect through the official `@modelcontextprotocol/ext-apps` `App` bridge** (versioned `ui/initialize` handshake); a hand-rolled raw-`postMessage` widget renders blank in real hosts. Since the widget imports an npm package, bundle it (esbuild) and inline it into the served HTML. See `examples/hello-mcp-apps` and [docs/guides/mcp-apps-widgets.md](docs/guides/mcp-apps-widgets.md). **Host extensions (P1-7 phase 1a).** Hosts read metadata beyond MCP Apps — ChatGPT's `openai/*` keys, Claude's `_meta.ui.domain` — and the framework carries it through **generic, checked seams, never a host vocabulary**: `@tool({icons, annotations, extend})`, `@resource/@appResource({title, icons, extend})`, `MCPServerConfig.{title, icons, websiteUrl, capabilities}`. `extend` takes `toolFragment({ui?, annotations?, meta?, check?})` / `resourceFragment({meta?, check?})`; merging and every fragment `check` run **at decoration** against the resolved options (incl. the real `input:` schema), so a broken host rule fails at the decorator line — a conflicting value, a duplicate key, `meta.ui` (use `ui:`), `io.modelcontextprotocol/*`, or non-JSON throws there. `@appResource` fixes the mcp-app MIME, requires `ui://`, and emits the typed `_meta.ui` (csp, permissions, domain, prefersBorder) on the **`resources/read` content item** (the spec's placement; the list entry carries none). A resource method may return `resourceContent({text}|{blob}, {mimeType?, meta?})` (blob → base64; per-call meta wins, `ui` merged key by key); unbranded returns are unchanged. `ui: {visibility: ['app']}` with no `resourceUri` is valid. **Visibility, entrypoints and annotations are presentation hints, never authorization.** `confirm:` implies `destructiveHint: true`, and `confirm:` + `readOnlyHint: true` throws. `capabilities` accepts only `extensions`/`experimental` (runtime-checked) and reaches both `initialize` and `server/discover`. **Phase 1b:** `contributeCapabilities(app, {extensions?, experimental?})` adds capabilities from code (a **constant** `MCP_CAPABILITIES` binding — `buildServer` is synchronous and reads each contribution binding's own value on every build, so stateless HTTP sees one on the next request; returns an `Installed` retracting via `revertOwned`; the same entry declared differently by two sources throws **at the `contributeCapabilities` call** — a conflict found only at build time would fail every new connection after `start()` — and `start()` re-checks the full set). Per request, `MCPBindings.REQUEST_META` is the frozen `params._meta` (client-asserted) and `MCPBindings.REQUEST_MOUNT` the HTTP mount (`installMcpHttp({path, host})` — server config). **Prefer one mount per host over `clientInfo`** for per-host presentation: it is trusted and works on every era, including stateless 2025 where `clientInfo` is absent. `@appResource({domain: fn})` resolves the widget domain per `resources/read`, after `@authorize`; a per-call `resourceContent` `ui.domain` still wins (and then the function is not run). An in-process `callTool` shadows the outer request's `REQUEST_CLIENT`/`REQUEST_META`/`REQUEST_MOUNT`. **Duplicate tool names throw at `start()`** (the same class bound twice is fine). `buildServer()` never throws on them — under stateless HTTP it runs per request — so a duplicate mounted later (a `perSession` binder, a plugin) is resolved **root-nearest first**: an app-level tool beats one bound in a child context, and if the winner is scope-hidden from a caller the name is hidden, never served by the loser. The conflict is logged once per app and pair. A child binding with the **same key** still overrides its parent, as everywhere in the container. Non-`ui` `_meta` keys need a vendor prefix (`openai/x`, `com.example/x`). Typed `openai/*` helpers live **outside the core**, in `@agentback/mcp-openai` (see the package list), so a moving host spec never touches `@agentback/mcp` — see [docs/proposals/host-extensions.md](docs/proposals/host-extensions.md).

## Deps and versioning

Default policy: **bump everything to the latest** with `ncu --workspaces --root -u --cooldown 1d --dep prod,dev,optional,packageManager --reject '@types/node,mcp-client-1-*'` (monorepo-aware), then `pnpm install` from a clean `pnpm-lock.yaml` and run `pnpm verify`.

- **`--cooldown 1d` matches pnpm's supply-chain age window** (see pnpm quirks below). Without it ncu picks versions hours old; pnpm then either fails the install or silently appends them to `minimumReleaseAgeExclude`, bypassing the policy nobody chose to bypass.
- **`--dep` omits `peer`**: ncu 23 rewrites peer ranges by default (`>=0.45.2 <1` → `^0.45.3`), which upgrades nothing for us and narrows what consumers may install. Moving a peer floor is a compatibility decision — make it by hand.
- **A clean lockfile means clean `node_modules` too.** pnpm reuses resolutions from `node_modules/.pnpm/lock.yaml` when `pnpm-lock.yaml` is missing, so deleting only the lockfile can resurrect versions from an earlier, abandoned install.

Exceptions to "latest", and why:

- **MCP TypeScript SDK is on v2, which is a package _split_, not a version bump.** The monolithic `@modelcontextprotocol/sdk` (v1) is gone from this workspace; the MCP packages depend on `@modelcontextprotocol/server` (server + runtime-neutral auth/errors), `@modelcontextprotocol/client` (client + transports), `@modelcontextprotocol/node` (`NodeStreamableHTTPServerTransport`, for the Express host) and `@modelcontextprotocol/express` (`requireBearerAuth`). `ncu` will not find these from a `@modelcontextprotocol/sdk` entry — there is nothing to bump, the name changed. Notes:
  - **Do not reintroduce `@modelcontextprotocol/server-legacy`.** It is a frozen v1 copy; every helper this repo needed exists in `/server` or `/express`.
  - **`MCPBindings.REQUEST_INFO` is the Web `Request`** (v1 handed a header record). Read headers with `info.headers.get('x-payment')` — `Headers` lookups are case-insensitive, so no manual case-folding helper is needed; the URL and method are now reachable too. Both hosts populate it (the Node/Express transport converts `IncomingMessage`), covered end-to-end by `mcp-http`'s `request-info.integration.ts`.
  - **Don't hand-roll bearer auth.** `/server` exports a runtime-neutral `requireBearerAuth` (`(Request) => AuthInfo | Response`) for the fetch/edge host and `/express` exports the Express middleware. v1 had only the Express one, which is why `fetch.ts` used to carry a copy — it doesn't any more.
  - **Serving a `.well-known` document by hand means answering `OPTIONS` by hand.** v1's `metadataHandler` bundled `cors()`; browser MCP clients preflight discovery (custom `MCP-Protocol-Version` header), and Express's built-in OPTIONS reply carries `Allow:` but no CORS headers. Use `PUBLIC_DISCOVERY_CORS` from `@agentback/mcp-http`.
  - **Token verifiers must throw the v2 `OAuthError`** (`new OAuthError(OAuthErrorCode.InvalidToken, …)`). `requireBearerAuth` classifies by that class — a legacy error class or a plain `Error` falls through as unexpected and turns an invalid token into an HTTP **500** instead of a 401.
  - **v2 still speaks the 2025 protocol era by default.** Nothing here puts a `2026-07-28` byte on the wire; adopting that revision (stateless core, `createMcpHandler`, MRTR/`requestState`) is a separate, opt-in change.
  - `@modelcontextprotocol/ext-apps` (the MCP Apps widget bridge used by `examples/hello-mcp-apps`) is on **v2** since ext-apps 2.0 (peers `@modelcontextprotocol/core|client|server ^2`). The remaining **v1** `@modelcontextprotocol/sdk` copies are the deliberate `mcp-client-1-*` back-compat pins in `mcp-http` and a transitive dep of the third-party `@anthropic-ai/claude-agent-sdk` (via `claude-agent-acp` in `hello-agent-console`, and `files-sdk`'s peer graph) — none is imported by an `@agentback/*` package.
- **Spell out `--workspaces`; never write `-ws`.** Older ncu read `-ws` as `--workspaces`; ncu 23 parses it as `-w -s`, and `-s` is `--silent` — the command exits 0, prints nothing, and upgrades nothing, which looks exactly like "already up to date". A real run prints a `Checking …` line per workspace package.
- **`@types/node`** — pinned with `~` to the **minimum Node version in `engines`** (`>=22.18` → `~22.18.x`), in the root `package.json` and the `create-agentback` templates. Types newer than the floor let code compile against APIs a supported Node lacks; a caret would float to later 22.x minors and reopen that gap. Excluded from `ncu` (`--reject`); move it only together with the `engines` floor.
- **`mcp-client-1-11`/`-1-17`/`-1-29`** (`packages/mcp-http` devDeps) are aliases to exact **old** `@modelcontextprotocol/sdk` 1.x releases — the back-compat matrix for 2025-era clients. Never bump them; `ncu` would collapse all three onto the newest 1.x and silently delete the coverage.
- **TypeScript is installed side-by-side: TS 7 for the `tsc` CLI, TS 6 as the `typescript` module.** TS 7 is the native Go compiler and **no longer ships the JS compiler API** — its `exports['.']` resolves to `lib/version.cjs`, so `require('typescript')` yields only `{version, versionMajorMinor}` (no `createProgram`, no `tsserver.js`). Tools that consume the API programmatically — `@typescript-eslint` (reads `ts.ModuleKind` at module load), editor language services — break against it, and every `@typescript-eslint` release through `8.63.0` still caps at `peer typescript: >=4.8.4 <6.1.0`. Per Microsoft's [side-by-side guidance](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/), the two `devDependencies` are:
  ```json
  "typescript": "npm:@typescript/typescript6@^6.0.2",   // the module tools import + its tsc6 bin
  "@typescript/native": "npm:typescript@~7.0.2"          // TS 7, provides the tsc bin
  ```
  Net effect, all deterministic from the lockfile (verified across a nuke + `--frozen-lockfile` reinstall): `tsc` → **TS 7** (fast builds), `tsc6` → TS 6, and `require('typescript')` / `@typescript-eslint` / editor tsserver → **TS 6** (full API restored, so `pnpm lint` and IDE type-checking both work). Both packages ship a `tsc` bin (a collision), but pnpm links TS 7's; that pick only affects build **speed**, never correctness — the eslint/editor fix rides on the `typescript` **package-name alias**, not the bin. Keep the build scripts calling bare `tsc`. Don't try to inject a TS 6 copy into the eslint packages via `packageExtensions` — `typescript` is a **peer** there and peer resolution wins over an injected dependency; aliasing the top-level `typescript` name is the only thing that works. Collapse this back to a single `typescript: ~7` once `@typescript-eslint` supports TS 7 and TS 7 ships a language service.
- **`express` is on `^5`** (migrated from `^4`). The migration was low-risk because `RestServer.toExpressPath` only emits simple `:name` params (never `*`/`:name?`/regex paths — the path-to-regexp v8 breakages), `req.query` is only read, and error flow already uses explicit `catch → next(err)`. `multer@^2` + `body-parser@^2` are already v5-ready. Keep new framework routes free of bare-wildcard paths (`app.get('*')` must be `app.get('/*splat')` under path-to-regexp v8).

When `ncu` produces a result that won't build, prefer pinning back the offender (with a one-line reason in the commit message) over patching code, unless the upgrade was the goal.

### pnpm 12 quirks worth knowing

- **Supply-chain age policy**: pnpm (11+) rejects lockfile entries published within a recent window (currently ~24h). If install fails with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`, pin the offending dep one patch/minor older. When you deliberately want a just-published version, `pnpm add` appends it (and every optional platform binary it pulls in) to `minimumReleaseAgeExclude` in `pnpm-workspace.yaml` — commit those entries, or CI's `pnpm install --frozen-lockfile` will trip the same check. They become no-ops once the version ages past the window.
- **`pnpm-workspace.yaml` `allowBuilds`**: pnpm (11+) requires per-package opt-in for postinstall scripts. The first install on a fresh machine writes `allowBuilds: { '<pkg>': set this to true or false }` placeholders into `pnpm-workspace.yaml`; replace `set this to ...` with `true` or `false` and rerun. Don't commit placeholders.
- **`verifyDepsBeforeRun: false`** is set in `pnpm-workspace.yaml` — otherwise pnpm runs `pnpm install` before any `pnpm <script>` whose deps look stale, which re-checks the supply-chain policy inside scripts that don't need re-resolution. **pnpm reads its settings from `pnpm-workspace.yaml`, not `.npmrc`**: this setting used to live in `.npmrc` (as `verify-deps-before-run=false`, beside a `minimum-release-age=0`) and both were silently ignored — the pre-run install still happened and the age policy stayed on. Put new pnpm settings in the YAML, where since pnpm 12 an unrecognized key fails the command (`ERR_PNPM_UNRECOGNIZED_WORKSPACE_SETTINGS`) instead of being dropped.
- **The `console` ↔ `console-agents`/`console-chat` cycle is deliberate**, and since pnpm 11.27 a cycle is a hard `ERR_PNPM_TASK_CYCLE` for a sorted `pnpm -r run`. This applies to `pnpm -r exec` too, not just `run`. The root `build`/`typecheck:client`/`clean` and `release.yml`'s version-bump `exec` pass `--no-sort` (none depends on order); keep it on any new recursive run or exec over those packages rather than setting `ignoreWorkspaceCycles`, which would also hide an accidental cycle. (`pnpm -r publish` is unaffected — verified with `--dry-run`.)
- **pnpm 12 pins itself in the lockfile** (a leading `packageManagerDependencies` document with integrity hashes for `pnpm`/`@pnpm/exe`), so bumping `packageManager` changes `pnpm-lock.yaml` too.

## Documentation surfaces (keep in sync with features)

When you add or materially change a **major feature** (a new package, decorator, port/adapter, or capability), update every surface it touches **in the same change** — doc drift is a recurring failure here. Run through this list:

- **Package README** (`packages/<pkg>/README.md`) — exports, a usage snippet, and where it sits in the layering.
- **`docs/packages.md`** — the catalog row (one line per package).
- **The concept/guide doc** under `docs/` (e.g. `docs/actor-model.md`, a `docs/guides/*.md`, or `docs/concepts/*.md`) — the authoritative how-it-works.
- **`docs/README.md`** — link the new doc/example from the learning-path tables.
- **The agent skill** — `skills/agentback/SKILL.md` (routing question + the packages/capability table) and a `skills/agentback/references/*.md` page. This is the agent-facing manual; without it, coding agents won't discover the feature.
- **`CLAUDE.md`** — the architecture "New capability packages" list and any rules the feature changes.

## Releasing

Versioning is **lockstep**: every `@agentback/*` package + `create-agentback` shares one version and releases together. Internal deps use `workspace:~`, which pnpm rewrites to `~<version>` at publish time (so patches propagate to consumers; verify with `pnpm -F <pkg> pack` + inspect the packed `package.json`). To cut `X.Y.Z`:

1. **Bump** every `packages/*/package.json` `version` to `X.Y.Z` (lockstep — do not bump one package alone; `create-agentback`'s scaffolded version range is derived from its own version).
2. **Verify**: `pnpm install && pnpm build && pnpm test` all green.
3. **Commit** (`chore(release): lockstep X.Y.Z`) and push.
4. **Publish** (OTP-gated, so run interactively): `pnpm -r publish --access public --no-git-checks`. Publishes in dependency order and **skips versions already on the registry**, so re-running after an OTP timeout is safe.
5. **Tag + push** — npm publish touches nothing in git, so tag the release commit and push it (otherwise the registry and repo history drift apart):
   ```bash
   git tag vX.Y.Z && git push origin vX.Y.Z
   gh release create vX.Y.Z --latest --title vX.Y.Z --notes "…"   # optional, matches v0.1.0+
   ```
6. **Bump dependent repos** (e.g. the demo) to `^X.Y.Z` and re-verify against the published packages.

Right after a publish, a consumer `npm install` can briefly 404 the new version (registry/CDN propagation lag) even though `npm view <pkg> version` shows it — retry with `--prefer-online` before assuming a partial release.

## CI

`.github/workflows/ci.yml` runs, on Node 22.18, 24 and 26 (the `engines` floor; pnpm 12 itself needs ≥ 18): `pnpm install --frozen-lockfile` → **`pnpm konsistent`** (structural conventions, fails in seconds) → **`pnpm check:generated`** (committed generated files are in sync with their sources) → **`pnpm lint`** (eslint + prettier --check; no build needed) → `pnpm build` → **`pnpm typecheck:client`** → `pnpm test`, plus a separate **validate-templates** job (`pnpm build` → `node scripts/validate-templates.mjs`). The lockfile must be committed in sync with `package.json` changes or CI fails at install.

**Run `pnpm verify` before pushing — it mirrors CI** (konsistent + check:generated + lint + build + typecheck:client + test + validate-templates + build:site). `pnpm build`/`pnpm test` alone are **not** sufficient: esbuild bundles the client `.tsx` without type-checking and vitest runs only the server `dist/`, so neither catches client-bundle type errors. The CI-only `typecheck:client` step (`tsc -p tsconfig.client.json --noEmit` per UI package) is the one that does — e.g. a client file importing from `src/lib`/`src/model.ts` must be inside that package's `tsconfig.client.json` `include`.

## Docs diagrams are SVG, and the mapping is positional

Mermaid blocks stay inline in the markdown as the **source of truth**; the site
renders a hand-laid `website/diagrams/<doc>-<n>.svg` per block and tucks the
mermaid under a `<details>`. See `website/diagrams/STYLE.md` — those SVGs are
embedded via `<img>`, so **no web fonts, no scripts, no `<foreignObject>`**
(that is why they use system mono and the light site palette rather than the
dark standalone diagrams in `docs/architecture/diagrams/*.html`).

**The filename→block mapping is positional.** Inserting a mermaid block into the
middle of a doc re-points every SVG after it at the wrong block. Each SVG
therefore carries `<!-- Source: <doc> mermaid block <n> ("<section>") -->` and
`build:site` fails on a missing, mismatched, or absent comment. When you add or
remove a diagram: renumber the SVGs after it and update their Source comments.

`pnpm verify` runs `build:site` for this reason — a docs-only change can break
the site deploy, and it did (three merges shipped with a broken deploy before
the check existed).

## Links in docs are checked at build time

`build:site` fails on a repo-relative link, in any page it ships (`DOC_PAGES` +
`docs/blog/**`), whose target does not exist in the repo. Linking a path the
site does **not** render is fine — `mapTarget` rewrites it to a GitHub URL — but
the path has to be real.

The check runs on the **sources**, inside `rewriteHref`, not on `dist`. That is
load-bearing: `mapTarget` turns anything unshipped into a GitHub URL, so a
typo'd `docs/guides/typo.md` becomes a well-formed link to a GitHub 404 that no
check against the built output can see. A dist-only version of this check was
written first and passed a deliberately broken link. A second pass over `dist`
also runs, catching the different failure of a page that was linked but never
emitted.

## Merging PRs (rebase-merge)

This repo merges PRs with **rebase-merge** (linear history on `main`, no merge nodes). Two consequences for how you work on a feature branch:

- **Never create a merge commit on a PR branch.** GitHub's rebase-merge (`gh pr merge --rebase`) **refuses** a branch whose history contains a merge commit (`GraphQL: This branch can't be rebased`). To pull in `main`, **rebase** onto it (`git fetch origin && git rebase origin/main`), don't `git merge origin/main`. If a merge commit already snuck in, linearize with `git rebase origin/main` (drops the merge) before merging — but that replays every commit, so see the next point.
- **`pnpm-lock.yaml` conflicts during a rebase are expected and noisy** — every replayed commit that touched the lockfile can re-conflict against `main`'s lockfile. Rebase with `-X theirs` (auto-resolves lockfile conflicts in favor of the replayed commits — verified safe when your commits don't edit `pnpm-workspace.yaml`), then run **one** `pnpm install` at the end to reconcile the lockfile against all `package.json`s and `git commit --amend` it into the final commit. Always `pnpm verify` the rebased tip before force-pushing (`git push --force-with-lease`) — a rebase can produce a different tree than the pre-rebase branch.
