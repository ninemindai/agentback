One Zod contract, four hosts

A tool used to have two readers: the model that calls it and the client that lists it. Now the host reads it too. ChatGPT looks for openai/* keys, and Claude looks for a widget domain. AgentBack adds those keys to the same @tool and checks them when the decorator runs, so one Zod schema still describes every surface.

The contract

Start with a schema and a method. Nothing here is host-specific:

const Library = z.object({parts: z.array(Part)});

@tool('parts_library', {
  title: 'Parts Library',
  output: Library,
  annotations: {readOnlyHint: true},
  ui: {resourceUri: 'ui://bits/library'},
})
async library(): Promise<z.infer<typeof Library>> { … }

That declaration is an MCP tool with an output schema, and an MCP Apps tool whose result a conformant host renders through the linked ui:// widget. The widget receives the result's structuredContent, which is the Library shape. A REST route on an @api controller that declares response: Library validates its responses against the same schema object.

The host layer

ChatGPT can open a tool from its sidebar. It calls a sidebar ("global") entrypoint with {} as the arguments, so the tool's input must accept an empty object. That rule belongs to ChatGPT, not to MCP, so it ships as a fragment: 

const sidebarEntrypoint = toolFragment({
  meta: {'openai/ui': {entrypoints: [{type: 'global'}]}},
  check: ({input}) => {
    if (input && !(input as z.ZodType).safeParse({}).success) {
      throw new Error('a global entrypoint must accept {} as its input');
    }
  },
});

@tool('parts_library', {…, extend: [sidebarEntrypoint]})

The check runs when @tool is applied, with the real input schema in hand. If someone later adds a required field, the build fails at the decorator line and names the tool. The alternative is finding out in ChatGPT, where the entrypoint just does nothing.

Claude renders each widget on its own sandbox origin, derived from the URL you add as a connector. That is a resource-side fact, so it goes on the widget: 

@appResource('ui://bits/library', {domain: claudeDomain(publicUrl)})
libraryWidget() { return WIDGET_HTML; }

What the checks refuse

A passthrough _meta would accept all of this and fail later, somewhere else. The seams refuse it when the decorator runs:

  • the same key set by two fragments;
  • a key MCP reserves for itself (ui, io.modelcontextprotocol/*);
  • a key without a vendor prefix (openai/ui and com.example/x are fine; a bare ui2 is not);
  • an annotation hint that is not a boolean;
  • an icon without a src;
  • a confirm: tool that also claims to be read-only.

None of these hints authorize anything. Visibility, entrypoints and annotations change how a host presents a tool. Who may call it is still decided by @authorize.

Why the core holds no host vocabulary

OpenAI's extensions are new and still moving, and Claude has exactly one convention so far. Typed openai/* helpers in the core would put a moving spec into every app's dependency graph. So the core ships generic, checked seams, and the host words live outside it.

The typed ChatGPT words now exist, in their own package. @agentback/mcp-openai is built only on those seams: openaiUi({entrypoints}) is the fragment above with the check written for you, and installSettings adds a per-user settings page. When OpenAI's spec moves, that package moves. @agentback/mcp and your @tool stay as they are.

One mount per host

Sometimes the same widget must look different in each host. A client names itself in clientInfo, but the client asserts that name, and a stateless 2025 request does not send it at all. A mount is server configuration. Serve each host its own path, such as installMcpHttp(app, {path: '/mcp/chatgpt', host: 'chatgpt'}). Then a tool or a widget's domain function reads the host from MCPBindings.REQUEST_MOUNT, on every protocol era.
