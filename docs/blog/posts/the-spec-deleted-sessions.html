The spec deleted sessions. Your tools never noticed.

MCP's 2026-07-28 revision removes protocol-level sessions, the GET stream, and resumability. AgentBack 0.9.0 serves it by default — and 2025-era clients from the same URL — without a single @tool changing. That insulation is the whole argument this blog has been making, finally getting tested by something real.

A protocol revision that deletes a core mechanism is the kind of event that tells you what your abstractions were actually worth. If your framework had spread session identity through its middle — a session id threaded into handlers, per-session caches, a discovery step that ran once per connection — then "sessions are gone" is a rewrite.

It wasn't, here. The tool you wrote in 0.8 is byte-for-byte the tool that runs on the new revision: 

@tool('forecast', {input: ForecastIn, output: ForecastOut})
async forecast(input: z.infer<typeof ForecastIn>) { … }

Nothing in that declaration ever mentioned a session, because a tool is a projection of a schema, not a participant in a transport. The transport changed underneath it. It kept working.

What the revision actually took away

The 2026-07-28 Streamable HTTP binding is smaller than its predecessor, not larger. It removes the Mcp-Session-Id handshake, the standalone GET stream, and resumable SSE via Last-Event-ID. Every message is its own POST. Server-to-client interactions that used to be server-initiated requests are now embedded in results as input requests — Multi Round-Trip Requests, or MRTR.

The practical consequence is operational rather than syntactic: with no session, there is no affinity. An endpoint scales behind plain round-robin with no shared storage, because every request builds and tears down its own server. That is a genuinely better shape for anything running more than one instance.

Two eras, one endpoint, one line back

You do not choose an era. protocol: 'both' — the default in 0.9.0 on both the stdio and HTTP surfaces — serves the new revision and 2025-era traffic from the same URL. A client that speaks the old handshake gets the old handshake. A client that sends a per-request envelope gets the new one. Neither is configured; both are detected.

We did not take that on faith. The dual-era path is verified against three released 1.x SDKs — 1.11.0, 1.17.0, 1.29.0 — covering every 2025 revision, on top of the current client. And because a default that cannot be undone is not a default but a migration, the rollback is one line: 

await installMcpHttp(app, {protocol: 'legacy'});
// or once, app-wide — the HTTP mount inherits it:
app.configure('servers.MCPServer').to({protocol: 'legacy'});

Setting it on the server config rolls back stdio and /mcp together. An earlier cut rolled back only stdio and quietly left the endpoint on the new revision — a documented one-line rollback that did half the job, which is worst precisely when someone is reaching for it mid-incident.

One exception keeps the flip safe. Resumable SSE is a session feature with no replacement in the new revision, so if you set an eventStore and do not name a protocol, you stay on sessions. A default should never silently delete a capability you asked for by name.

Sessions were never in your code, so they were cheap to remove

The one place sessions were visible in userland was perSession — the hook for per-user tool discovery. Under the new revision it becomes per-request discovery. Same binder, same signature, same security contract; it just runs more often.

That worked because the DI container was already doing the load-bearing part. A per-session server was a child Context resolved from the application context. A per-request server is the same child context with a shorter life. The framework's own seam did not care how long "a request's worth of state" lasts, which is exactly what you want from a seam.

The honest cost: a binder that does an entitlement lookup now does it on every request instead of once per connection. That is a quiet load multiplier rather than an error, which is the worst way for a problem to arrive — so the framework ships the answer rather than leaving each app to rediscover it: 

perSession: cachedPerPrincipal(
  principal => entitlements.toolsFor(principal?.extra?.sub),   // cached
  (ctx, classes) => classes.forEach(C => addTool(ctx, C)),      // every request
  {keyOf: p => `${p?.extra?.sub ?? 'anon'}`, ttlMs: 60_000},
)

Only the lookup is cached. The apply step runs fresh against that request's own context, and a Context is never cached — it is closed when its request ends.

keyOf is required, deliberately. The obvious choice — AuthInfo.clientId — is wrong under OAuth, where it is the client application id shared by every end user of that app. Keying a cache on it hands one user's entitlement lookup to another. Which claim identifies a subject varies by identity provider, so the framework refuses to guess a security boundary and makes you name it.

The bug shape statelessness invites

Two real bugs came out of this work, and they had the same shape. Naming it is more useful than claiming there weren't any.

When a request path moves from per-session to per-request construction, every value the session path computed once must be re-derived per request. That sounds obvious. What makes it dangerous is how the mistake looks in a diff: 

// session path
const scoped = authEnabled ? {scopes: authInfo?.scopes ?? []} : undefined;

// stateless factory, first cut — looks equivalent, is not
const scoped = ctx.authInfo ? {scopes: ctx.authInfo.scopes} : {};

The consumer treats undefined as "skip scope filtering entirely." Under optional auth, an anonymous caller had no authInfo, fell through to {}, and every @tool({scope}) became visible and callable — @tool({scope}) is a visibility gate, so nothing downstream re-checks it. The second bug was the same shape wearing different clothes: a confirmation store that lived per instance vanished between the two requests of a confirm: round trip, so every valid token was rejected.

Both are fixed, both are pinned by regression tests, and both are written into the framework's own contributor docs as invariants — not because the fix was hard, but because the shape will come back. Anything that used to be computed once per session is now a candidate.

Confirmation gets a native face

confirm: tools have always used a token dance: the server answers confirmation_required with a single-use token, the caller repeats the call carrying it. The new revision's MRTR lets a conformant host render a real dialog instead — so confirm: now picks its presentation per request.

A client on the new era that declared the elicitation capability gets a native input_required result. Everyone else — the 2025 era, a modern client that cannot prompt, and every programmatic caller like the CLI or an in-app agent — gets the token dance. Era alone is not the gate, and that detail cost us a bug worth repeating: the SDK raises a hard protocol error for an elicitation the client never declared, so gating on era would have turned a confirmation into a crash.

One thing did not move. The confirmation store remains the sole authority on both paths. MRTR's requestState only transports a token the server already issued, because requestState is client-echoed and the spec treats it as attacker-controlled. A round trip having happened is not the same as a human having said yes.

A MUST we had never met

The revision also prompted us to re-read a clause we had been failing since long before it: servers MUST validate the Origin header on incoming connections. Not new in 2026-07-28 — identical wording sits in 2025-06-18 and dates to 2025-03-26. Enabling the check only when someone happened to configure an allowlist was never conformant on any revision.

It is on by default now, and the allowlist is derived from your rest.cors config rather than declared a second time — because those origins already are your statement of which browsers may call the app. Each entry is matched at the precision it was declared at: a CORS origin string exactly, scheme and port included; a CORS regex by testing it; an explicitly-configured allowedOrigins by hostname, because that is its shipped behaviour and narrowing it would break callers who already set it.

This is safe to default because a missing Origin passes. Only browsers send the header, so no MCP client, no curl, no stdio bridge is affected. The only request that can newly fail is a browser one, which is the case the guard exists for. The full posture — bearer auth, framework strategies, rate limiting and this guard together — is in securing MCP over HTTP.

What the revision was really a test of

The claim this blog keeps making is that a service should have one source of truth and that every surface should be a projection of it. The usual objection is that projections are fine until reality changes shape, and then the abstraction is a liability.

This was that test. A protocol removed its session model, its streaming endpoint, and its resumability story. The framework's transport layer absorbed it, the DI container turned out to have been doing the hard part all along, and the surface you author — a Zod schema on a decorator — did not move.

The work that remains is the honest kind: resumable SSE has no replacement in the new revision, so retiring the session machinery for good is a breaking capability removal rather than a cleanup, and it is still gated on that. Nothing is on the clock. But the default is now the era the ecosystem is moving to, and getting there cost your application code exactly nothing.
