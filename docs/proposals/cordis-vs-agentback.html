Two coherences: Cordis and AgentBack, mechanism by mechanism

Both frameworks bet on AI-led development, from opposite ends. AgentBack makes every boundary derive from one artifact; Cordis makes every mount revertible and every dependency reactive. This report draws the machinery so the difference is pointable-at.

AgentBack — boundary coherence (space) Cordis — lifecycle coherence (time)

1The two theses are orthogonal axes

AgentBack's claim: a single Zod schema, declared once on a decorator, is the validator, the TS type, the OpenAPI document, the MCP tool contract, and the rendered docs — so the boundaries cannot disagree with each other. Cordis's claim, formalized in the 2026 DeepSeek-AI/PKU preprint A Programming Paradigm for Spatiotemporal Composability: every context transformation carries an inverse the runtime tracks, so a component can be removed and the system provably returns to the state it would have had without it. One is a claim about artifacts in space; the other about effects in time. Neither framework has an answer on the other's axis.

2Dependency machinery: typed keys vs an ambient Proxy

AgentBack keeps LoopBack's container: values bound under typed keys, injected into constructor slots, resolved when the app starts. Cordis has no binding keys at all — the context is the container, services are properties on it, and a Proxy get handler polices access: read a service you never declared in inject and it throws. That is a coeffect check enforced at property access.

AgentBack

// typed key, checked injection, resolved at start()
const DB = BindingKey.create<Db>('db');
app.bind(DB).toClass(DrizzleClient);

class Reports {
  constructor(@inject(DB) private db: Db) {}
}

Cordis

// service = property on ctx, declared coeffect
ctx.provide('db', new DrizzleClient(ctx));

ctx.inject(['db'], (ctx) => {
  ctx.db.query(...)   // ok: declared
  ctx.timer            // throws: not injected
});

3The load-bearing difference: what happens on change

Swap a database adapter in a running system. AgentBack is not blind to runtime change — ContextView/ContextObserver track bind/unbind live, which is how the middleware chain and extension points pick up late registrations without a restart. But that reactivity is discovery-level: it re-enumerates collections. A constructor-injected provider like the database client resolved once at instantiation, and nothing unwinds what a removed binding already did — so for a provider swap the honest answer is restart. Cordis's answer is the entire framework: the provider's disposal flips the epoch of every dependent (a string concatenating its providers' fiber UIDs), and each dependent unloads — replaying its accumulated inverses in reverse — then reloads against the new provider. Fibers not depending on the database never notice.

5What the paper actually proves

The metatheory (§4.4) is the part that elevates this above "plugin framework with good cleanup." In plain terms:

  • Recovery exactness · Thm 61 — running a fiber's accumulated inverse yields the state as if it had never begun, even with arbitrary interleaving from other fibers.
  • Ordering · Thm 63 — a fiber activates only when its dependencies are provided, and a provider outlives its consumers.
  • Resolution coherence · Thm 64 — a load runs against exactly one dependency resolution; if the world shifts mid-load, the transition diverts and unloads rather than half-applying.
  • Progress · Thm 66 — no deadlock, and a termination bound: reconfiguration storms settle.
  • Confluence · §4.4.5 — the dynamic history leaves no trace: any load/unload/reload sequence quiesces at the state a from-scratch boot would produce. This is the property a long-running, agent-edited process needs to avoid drift.

The honest caveats, which the paper owns: effects that emit past the process boundary (a network send, a paid API call) can only be withheld or compensated, never reverted (§6.1); dependency cycles leave both components permanently inactive (§6.5); and the validation is existence-and-adoption, not a controlled comparison (§5.3).

6Takeaways for AgentBack

Steal the disposer discipline

Every install* helper could return (and internally compose) an uninstall. No fibers, no proxies — just the invariant that mount functions return their inverse. The cheapest 20% of Cordis; buys the hot-swap option later. Most relevant to @agentback/plugin.

Name the restart trade

See-and-evolve currently means source edit + process restart. Defensible — but the paper is the sharpest account of what restart costs at agent edit-frequency. Now recorded as a known limit in agent-ergonomics.md, with the study at docs/proposals/cordis-spatiotemporal-composability.md.

Ports already are brokers

The paper's service-broker pattern (§6.2) — a stable interface absorbing provider swaps — is functionally what FileStore / JobQueue / ActorRuntime already are. The ports are the right stable seam if live adapter swapping ever becomes a requirement.

Non-takeaways, for the record: the ambient Proxy context trades away exactly what AgentBack is built on — typed keys, request scope, per-resolution isolation — and adopting the fiber machinery wholesale would be a second framework inside the framework. The value is the discipline (effects return their inverses) and the formal vocabulary, not the runtime.
